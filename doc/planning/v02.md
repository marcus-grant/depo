# Version 0.2 Planning

Post-MVP improvements. Nothing here ships until MVP (v0.1) is complete.

## Schema change readiness (READ BEFORE ANY SCHEMA CHANGE)

The migration guard shipped in `ft/migrations`: `repo_meta` holds
`schema_version`, stamped on init and read back, and server-starting
commands refuse to run when the DB is behind or ahead of the code's
`SCHEMA_VERSION` (both directions raise `SchemaVersionError`). What did
NOT ship is the migrate command that applies pending files. A stale DB is
detected and blocked but cannot be brought forward except by hand.

The first task that changes the schema must, in the same PR:

- Build the migrate command that applies pending `migration-M-m-p.sql`
  files, forward-only, triggered explicitly (never at startup). The
  selection helpers already exist (`pending_migrations`, `list_migrations`,
  `_migration_version` in `repo/sqlite.py`); wire a command over them.
- Refactor migration code out of `repo/sqlite.py` into its own module
  under `repo` (for example `repo/migrations.py`). It currently sits
  beside unrelated row-mapping and repo code; the migrate PR is where it
  earns its own module.
- Add the upgrade test deferred from MVP: a DB at version N upgrades to
  N+1 without data loss.
- Document the migration system in `doc/module/repo.md`: the shipped guard
  and the new command.

Bump `SCHEMA_VERSION` in `repo/schema/__init__.py` and the stamp in
`_schema.sql` together; they are a deliberate double-entry (noted in the
schema file). A mismatch between them is what the guard exists to catch.

## Honest status codes on htmx error surfaces

`htmx_error` hardcodes `status_code=200` so htmx will swap the error partial
into the DOM. htmx only swaps 2xx responses by default, and the 200 convention
grew up as a workaround for that.

The cost is that an auth failure, a validation failure, and a success are
indistinguishable on the wire. Monitoring, logging middleware, and any API
client hitting the same endpoint all see 200.

htmx exposes `htmx:beforeSwap`, where a handler can inspect
`evt.detail.xhr.status` and set `shouldSwap = true`, so a real 4xx can carry a
partial and still render. Honest status and rendered partial are not in
conflict.

- [ ] Add a client-side `htmx:beforeSwap` handler opting into swapping 4xx
      bodies
- [ ] Return real statuses from `htmx_error` rather than 200
- [ ] Two specs flip and must be updated:
      `TestAuthRequiredHandler::test_htmx_surface_returns_200_partial` and
      `TestUploadGate::test_htmx_rejection_carries_login_link`
- [ ] Update `doc/design/routes.md`, which documents the 200 as a temporary
      exception to the uniform-401 rule

This also answers the open question in the login form chrome block: htmx *can*
swap an error partial while preserving a 401, but only with a `beforeSwap`
handler. Plan the login error response on top of this.

## Ingest streaming redesign (rungs 3-5)

Rungs 1-2 (hash-named storage, durable seal-then-commit ordering) are
MVP; see [mvp](./mvp.md). These rungs remove the whole-payload-in-memory
design and are safe to build while the MVP operates. Order matters:
stage seams (rung 3) before streaming (rung 4) before async (rung 5).

The core problem: every upload path buffers the entire payload in RAM
(`request.body()`, `file.read()`), holds it live through hash, classify,
and store, and only enforces the 64MiB cap after buffering. The cap
protects the store, not memory. Concurrent large uploads multiply.

IO assumption: NVMe is the near-term deployment but SATA SSD (and
slower) servers are supported targets. Request-latency costs (fsync,
page-cache writes) stay fine there; what slower drives bound is
sustained aggregate ingress. Nothing in these rungs may assume
NVMe-class latency to be correct, only to be fast.

### Test discipline per rung

Every rung is one PR, and each follows the same sequence. The old suite
enforces old specs; tests breaking as rungs land are good signals to
trip over, proof we are testing the right things, not noise to
suppress.

- Before any development in a rung PR
  - [ ] Analyze the related test suite: which tests assert the spec
        being changed, which assert behavior that must survive
- RED phase: write tests for the new specs first
  - [ ] An outer e2e layer tracking the invariant behavior
        (upload -> code -> serve -> dedupe, all input paths) that
        must hold across every rung; in place before rung 3,
        keep green through 3-5
    - The existing suite may already hold a solid e2e layer that
      serves as this anchor as-is; explore the test tree first
      and decide what is already done before writing anything new
    - Exact shape of this outer red layer still undecided
  - [ ] Stage-level tests for the rung's new contracts
- GREEN phase: implementation only, until the new tests pass
- Then triage the contradicting reds from the old suite
  - [ ] Determine which old tests no longer hold valid assertions
        about the project; delete or modify them deliberately,
        each one a recorded spec change, never a blind fixup

### Rung 3: stage decomposition (pure refactor, no behavior change)

The representation of the payload (bytes vs path) currently leaks into
every layer, and each layer branches on it. Fix: one normalization
boundary, then every stage speaks the same types.

- Pipeline shape: parse -> spool -> classify -> verify -> persist
  - [ ] `UploadSource` DTO replaces the three `UploadParams` TypedDicts
    - chunks (async iterator), filename, declared_mime,
      requested_format
    - Route handlers shrink to content negotiation + adapter
      selection + response rendering
  - [ ] `StagedPayload` DTO as the spool stage output
    - tmp_path, size_b, hash_full, head prefix (~4KB), utf8 verdict
    - Computed from in-memory bytes at this rung; rung 4 swaps the
      internals without changing the contract
  - [ ] `classify(staged, hints)` consumes only prefix + hints +
        spool verdicts, never full content
    - URL detection applies only when size_b <= max_url_len
  - [ ] `verify` becomes its own stage after classification
    - Pillow decode for pictures, URL length check for links
    - Whole-content validation is first-class here, not
      special-cased inside `build_plan`

### Rung 4: real spooling (gated on b3c32 chunked hashing)

- [ ] Spool stage consumes the chunk iterator into `.incoming/`
  - Per chunk: byte count (abort the instant the cap is crossed,
    the genuine OOM guard), incremental b3c32 hash, incremental
    UTF-8/control-char check, head prefix capture
  - Buffered writes only; durability is one fsync at seal, never
    O_SYNC per chunk (per-chunk sync would be ruinous on SATA)
  - Chunk size 64KB-1MB; framework 8KB defaults show up in
    syscall-count profiles at high concurrency
- [ ] Routes switch to `request.stream()` / multipart part streams
  - Nothing upstream may touch `request.body()` first, error
    paths included
- [ ] Dedupe check moves to spool EOF (hash known); a duplicate
      never touches classify, verify, or the store
- [ ] `verify` hands Pillow the temp file, not bytes
- [ ] `WritePlan.payload_bytes` and `PayloadKind.BYTES` retire;
      `payload_path` always
  - Link URL extraction in `repo.insert` currently reads
    `plan.payload_bytes`; needs a home (plan.link_url exists)
- Deliberately no small-payload memory fast path
  - The page cache already keeps small spool files in RAM; one
    code path beats a threshold constant. Add a fast path inside
    the spool stage later only if profiling demands it, same
    `StagedPayload` contract out

### Rung 5: async pipeline, raise the size cap

- [ ] `ingest` async end-to-end; async b3c32 lands here
- [ ] Pillow and SQLite calls to a threadpool so they stop
      blocking the event loop
- [ ] Lift 64MiB to a policy decision; memory no longer scales
      with payload size
  - Cap policy may differ by deployment IO class; make it config,
    not a constant

### Later, enabled by the above

- Resumable / TUS-style uploads and deferred verification
  - Needs a durably-parked-but-unblessed state; spell it as a
    location or suffix convention (`.incoming/{hash}.part`),
    never absence-of-extension
